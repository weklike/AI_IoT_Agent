# 求职材料草案（v2.0）

投递前需本人阅读代码、完成演示并解释取舍。以下是已实现的工程能力；完整M4及真实模型质量另按验收证据判断。

- 使用三台独立MQTT软件客户端、FastAPI、SQLite与Vue实现充电会话、遥测监控、受限功率计划和运维处理闭环；保持单worker与单Agent运行槽位。
- 实现遥测双唯一键、重复/冲突/乱序处理、独立新鲜度判定，以及会话报告提交后ACK、持久化重发、整数能量积分和崩溃检查点恢复。
- 实现先降低并验证、再提高的站点分配流程，按未知控制结果计算保守功率上界；幂等记录与业务结果原子提交，部分失败保留真实确认状态。
- 实现九工具白名单、授权/证据校验、20/3/90+5秒预算，以及24篇版本化FTS5检索和同run引用绑定；区分模型替身、真实模型和真人语义复核。
- 实现告警持续观测与恢复、工单处理/验证关闭、只读巡检、三页面交互和事件复盘；用隔离MQTT、SQLite、Compose与Playwright保存可追溯证据。

2. online与data_fresh为何独立？报告持续收到时为什么仍可offline？
3. 整数Wh如何避免每次采样取整损失？重启后为何不补算停机能量？
4. 降低尚未确认时，为什么不能直接按新目标计算可用预算？
5. request_id幂等、未关闭工单唯一约束和控制generation分别解决什么？
6. ACK/applied、verified、unconfirmed、PARTIAL为何必须分开？
7. 告警确认、恢复与工单关闭为什么不是同一件事？
8. tool_call_id与provider_call_id为何分开？引用有出处为何仍需人工语义评审？
9. FTS5命中率与回答准确率有什么区别？为何不能称向量RAG？
10. 为什么使用单体SQLite、轮询和进程内工具足够支持这个作品？
