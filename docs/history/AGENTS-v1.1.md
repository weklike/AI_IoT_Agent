开始新会话或接手任务时，按顺序读取：

## 2. 固定目标与第一版范围

目标是完成适合汽车相关企业、物联网平台、AI 应用与全栈岗位校招的单机演示作品。必须能够解释关键实现，并用实际证据证明运行结果。

| 项目 | 第一版固定范围 |
|---|---|
| 设备 | 纯软件模拟，CHG-001、CHG-002、CHG-003 三台独立 MQTT 客户端 |
| 模拟场景 | normal、overheat、offline；offline 暂停遥测但保留控制订阅 |
| Agent | 一个业务 Agent；同时最多一个运行中的任务 |
| 工具 | get_device_status、get_device_history、get_fault_guide、create_work_order |
| 页面 | 设备总览、设备详情、Agent 对话；工单展示放在已有页面 |
| 后端 | FastAPI 单体，一个 Uvicorn worker |
| 数据库 | 本地 SQLite，七张核心表，WAL、外键与唯一约束 |
| 部署 | mqtt、backend、simulator、frontend 四个 Compose 服务 |
| 模型 | fixture 与 real 两种模式；真实模式先支持一个已验证的工具调用端点 |

不主动增加实体硬件、模型训练、地图、语音、支付、预约、多租户、微服务、消息中间件集群、向量数据库或多 Agent。MCP、流式回答和检索扩展属于第一版通过后的选做项，当前不实现。

MQTT 是设备通信协议；第一版 Agent 工具在后端进程内通过函数调用执行。不得把现有 MQTT 链路描述成已经实现 MCP over MQTT，也不得把两份本地故障说明称为向量 RAG。

## 4. 环境、依赖与仓库边界

- 用户电脑为 Ryzen 7 5800H、24 GB 内存。开发基准为 Linux/WSL2 + Docker；源码和 SQLite 放在 Linux 本地文件系统。
- WSL2 可从 6 个逻辑 CPU、12 GB 内存上限起步，SSD 预留 30—40 GB；这些是规划值，不能当作实测数据。
- 使用 Python 3.12、FastAPI、Pydantic 2、SQLAlchemy 2 + aiosqlite、paho-mqtt 2、Mosquitto 2、Vue 3、TypeScript、ECharts。前端构建使用 Node.js 22.12 或以上兼容版本。
- Python 统一使用 uv，前端统一使用 npm；提交 `uv.lock`、`package-lock.json`，不要同时引入多个包管理器锁文件。
- 第一次生成锁文件时解析兼容版本；以后从锁文件安装。不要为了通过测试而无关地升级整个依赖树或使用漂移的 latest 镜像。
- 新增依赖前先确认现有依赖无法合理承担该职责，记录用途和版本；不因个人偏好引入新的 ORM、Agent 框架或 UI 体系。
- 以 pyproject.toml 保证 backend、simulator 和测试环境中的 tests.support 可导入，不靠临时 PYTHONPATH 修补。
- 本机与容器分别配置数据库路径、MQTT 主机名；宿主机与容器不能同时写同一个 SQLite 文件。
- 宿主机演示端口只绑定 127.0.0.1。模型配置只传后端，不进入前端构建参数。

Git 操作必须保留用户已有修改。不得擅自执行 `git reset --hard`、`git clean -fd`、强制推送或重写历史。创建提交时只包含本次相关文件；在计划已授权的本地提交范围内推进，不把本地提交等同于外部推送或发布授权。

## 5. 模块职责与代码质量

| 模块 | 应承担的职责 | 不应承担的职责 |
|---|---|---|
| backend/app/api.py | HTTP 参数、响应、服务调用 | 直接拼接模型提示、在路由内复制全部业务规则 |
| telemetry/ | 接收校验、去重、顺序、新鲜度、查询统计 | 绕过合同补造缺失遥测 |
| mqtt/client.py | 连接、订阅、重连、消息交接 | 跨线程共享 AsyncSession |
| work_orders.py | 授权、证据、事务、OPEN 工单幂等 | 相信模型自行填写的工单编号或内部证据 |
| agent/ | provider 适配、工具 Schema、执行预算、轨迹 | 任意 shell、任意 SQL 或未注册设备控制 |
| simulator/ | 独立设备客户端、合成遥测、场景回执 | 直接写业务数据库 |
| frontend/ | 三页交互、可见状态、轮询、轨迹展示 | 持有模型密钥、自行裁决设备在线状态 |
| tests/、eval/ | 隔离夹具、行为测试、固定案例、结果记录 | 让测试替身进入 real 业务路径 |

代码要求：

- Python 接口、配置和核心数据结构给出类型；外部输入经 Pydantic 校验。TypeScript 使用明确类型，不以大面积 any 或忽略错误绕过编译。
- 遵循仓库已选格式与命名；注释解释约束和取舍，不重复翻译每一行代码。
- 复杂行为拆成可测试的业务函数。不要为了“架构完整”提前增加工厂、插件注册体系或多层空包装。
- 生产路径不能留固定答案、伪造成功、空实现或未处理的关键 TODO。允许尚未开发的阶段存在明确标注的骨架，不能对外宣称完成。
- 不用宽泛异常捕获后返回空列表掩盖错误；返回与合同一致的错误码，并记录必要关联 ID。
- 不在异步路径执行阻塞等待。模型 HTTP、数据库会话、MQTT 和后台任务均有明确生命周期与关闭路径。
- 日志保留 request_id、run_id、tool_call_id、设备 ID 等必要关联；不打印认证头、密钥或完整敏感配置。

## 6. 遥测、时钟与数据约束

完整字段、数值范围和 HTTP 路径以开发计划第 3、4 节为准，以下规则不得省略：

1. 数字拒绝字符串、布尔值、NaN、Infinity；额外字段、未知设备和主题不匹配必须处理。合法 JSON 时间与 UUID 字符串应能正常解析，必须有正向测试。
2. message_id 全局唯一，(device_id, boot_id, seq) 也唯一。完全重复不新增；键相同但内容不同记 conflict，不覆盖原记录。
3. 重复比较只包含设备业务字段，不包含后端 received_at 或性能日志时间。
4. 旧但合法的样本可进历史；当前快照只采用严格更新的 ts。重复、乱序、回放和 retained 消息不得刷新在线时间。
5. 数据新鲜度与连接状态独立。样本年龄不超过 10 秒且本进程已收到新鲜样本时 data_fresh=true；最后新鲜接收后超过 15 秒才 offline。
6. online 不代表数据一定新鲜。过期数据的 health_state 为 unknown，保留带时间的最后指标；前端和模型都不能称其为实时值。
7. 后端重启先显示 unknown，历史仍可查；不能拿旧持久化记录证明当前在线。
8. DataClock 提供带时区 UTC；deadline 与耗时使用真实单调时钟。测试只能冻结 DataClock，不能冻结超时机制。
9. 时间字段统一 sample_ts，空样本的数值/时间/年龄为 null，不能伪装成 0。
10. HTTP 历史窗口最多 24 小时、5000 行，超限明确拒绝；工具历史窗口为 1—60 分钟。统计使用完整窗口样本，展示下采样不影响统计。

遥测、快照、新鲜度在同一短事务更新。paho 网络回调通过线程安全入口把消息交给应用事件循环；一个消费者负责遥测入库，每个 HTTP/工具事务使用独立会话。

场景命令必须有 command_id 及匹配回执。Broker 发布成功不能直接变成 applied；等待 5 秒未确认则 timed_out，晚到回执单独记录。offline 是停止上报的模拟，按钮点击时不能立即显示设备已离线。

## 7. Agent 协议与执行预算

四个工具的模型侧参数固定如下，不能私自增加控制能力：

```text
get_device_status(device_id)
get_device_history(device_id, window_minutes)
get_fault_guide(reason_code)
create_work_order(device_id, reason_code)
```

create_work_order 的 ToolContext 由服务器注入，包含 run_id、内部 tool_call_id 与 allow_work_order；模型不能提供这些值。工具结果统一为 `{tool_call_id, ok, data, error}`。

| 约束 | 默认值 |
|---|---|
| 每轮模型请求 | 最多 6 次，包含最终回答请求 |
| 每轮工具执行 | 最多 8 次 |
| 单次模型请求 | 20 秒 |
| 单次工具执行 | 3 秒 |
| 整轮业务执行 | 90 秒 |
| 受管理清理 | 最多再加 5 秒，禁止启动新工具 |
| SQLite busy timeout | 每个连接 1000 ms |
| Agent 并发 | 1；其他新任务返回 429 AGENT_BUSY |

所有值来自统一 Settings。实际 await 时限取单步上限与剩余总预算的较小值；不能把表内单步上限相加后延长整轮 deadline。

- 完整保存 assistant 响应中的 tool_calls，先追加 assistant 消息，再按 provider_call_id 回传对应工具结果；内部 tool_call_id 与 provider ID 分开保存。
- 执行前验证整批工具名称、参数和剩余预算，再按顺序执行。未知工具、错误参数不能进入业务函数。
- 同时含正文和 tool calls 的响应仍走工具分支；最终空回答、畸形结构和重复协议 ID 返回 MODEL_PROTOCOL_ERROR。
- 覆盖“状态→历史→说明→建单→回答”的五次串行模型请求，不能只测合并查询的短流程。
- 第一版不做隐藏重试。401、429、工具失败、超时和预算耗尽都明确记录；real 失败不得静默切换 fixture。
- 数据结论必须来自实际工具结果；排查说明标 source_id/version；工单编号必须来自数据库结果。
- 工具输出和故障说明属于不可信业务数据，不能改变工具白名单、授权标志或执行规则。应用 Agent 不得读取开发会话凭据、项目 .env 或任意文件。
- completed 只表示执行流程正常结束，不能替代回答正确性验收。

## 8. 工单、幂等与事务

- allow_work_order 默认为 false；用户在本次业务任务中明确允许才暴露写工具，服务器仍须再次校验。开启写入选项不表示所有纯查询都应自动建单。
- 先查 request_id 幂等，再检查忙碌状态。同 ID 同 question/授权标志复用原 run；同 ID 不同内容返回 409。
- “查幂等→检查运行槽位→持久化 run→登记任务”由进程调度锁保护；模型等待不持有该锁。两个新请求同时到达只能接受一个。
- 同设备同原因最多一张 OPEN 工单，数据库部分唯一索引兜底。已有单返回真实 order_id、created=false。
- 后端只从本 run、本设备的成功只读工具记录选择证据。OVERHEAT/OFFLINE 的有效性按计划第 4.2 节重算；曾离线但写入前已恢复不能作为当前离线建单依据。
- 保存被选中的工具记录、原始样本 ID/时间及校验时间，不能只保存模型生成的解释。
- 工单变更与当前 tool_call 的结果在同一事务提交。提交边界超时后停止后续调度，等待受管理的完成/回滚，按当前调用 ID 恢复结果。
- 只查到同设备的旧工单不能证明本次成功。无法确认返回 WRITE_RESULT_UNKNOWN，禁止盲重试和成功声明。
- 模型请求期间不持有数据库事务或写锁；连接应用 WAL/外键/busy timeout，锁错误明确返回，不无限重试。
- 重启将遗留 queued/running 标为 interrupted，保留已提交工单；不自动重放模型或写工具。

## 9. 前端交互

- 页面只使用真实后端 API；开发占位、fixture 模式及 real 模式必须可区分。不能用静态数组或前端生成的工具轨迹冒充集成完成。
- 设备数据每 2 秒查询，Agent 状态每 1 秒查询；同一查询不重叠，离开路由时取消轮询，run 终态后停止该运行查询。
- 发起请求前生成并保存 request_id；网络重试复用，取得 run_id 后可刷新恢复。重复点击不能创建新的业务任务。
- 显示 loading、空数据、未知设备、服务断开、工具失败和超时；不无限转圈、不把失败显示成绿色成功。
- unknown、offline、过温和 stale 有文字说明；数字带单位和样本时间，不能只靠颜色传递状态。
- 1280×720 与 1920×1080 检查无遮挡、无横向溢出。维持三个页面，优先清晰可演示的业务布局。

## 10. 测试策略与资源隔离

只测试真实行为和具体风险，不为了覆盖率数字写与实现逐行对应的测试。关键业务规则与修复先复现失败，再实现或修正；低风险文案、样式变更用针对性检查即可。

| 修改范围 | 最低必要验证 |
|---|---|
| 遥测、时间、去重 | 合法 JSON 与拒绝输入、重复/冲突/乱序、10/15 秒边界；相关 MQTT 集成 |
| 工单、幂等、调度 | 授权、证据归属、并发、唯一约束、提交边界；重试行为 |
| Agent、provider、Schema | 消息配对、五轮流程、非法工具、错误返回、预算与超时 |
| API 合同 | 状态码、统一响应结构、空值与异常；受影响前端调用 |
| 页面交互 | typecheck、build、受影响 E2E；必要截图 |
| Compose、生命周期 | 就绪检查、依赖恢复、数据保留、后台任务结束 |
| 纯文档 | 引用、命令、版本和阈值一致性；不机械重跑模型评测 |

资源规则：

- 单元测试使用临时 SQLite 和固定 DataClock；集成/E2E/性能入口使用自己创建的 Compose 项目、卷、随机可用端口、MQTT 前缀及 client_id。
- 清理仅限本次创建的资源。重置必须满足 APP_ENV=test/eval 且路径位于本次临时目录；不能清空开发库或停止用户正在使用的服务。
- 真实模型评测使用相同 create_app、真实 API 与真实工具；关闭 MQTT 消费，在 lifespan 启动完成后加载固定数据。ASGI 客户端本身不能替代生命周期的启动与关闭。
- fixture 只替换模型响应，不能把数据库、工具、副作用和错误分支全部 mock 掉之后称为闭环通过。
- 工单的 20 并发测试直接作用于服务层并使用独立会话；Agent HTTP 接收并发另测两个新请求只能接受一个。
- pytest、Docker、浏览器或凭据不可用时记录 BLOCKED；缺少测试实现记录 NOT_RUN。不能用 skip、xfail 或空断言消除必须验收项。
- 先运行相关最小验证，修复后跑受影响流程。最终阶段按完整门槛执行；不要每次样式改动都重新做 60 分钟负载或 60 次模型评测。

```bash
# 真实模型评测与人工复核后的汇总
uv run python eval/run.py --mode real --repeat 3 --output artifacts/acceptance/real-model
uv run python eval/run.py --summarize artifacts/acceptance/real-model --review-file eval/manual-review.json
```

Playwright 系统依赖另外按 README 准备。真实评测需要后端本地可用的模型配置；不把密钥写到命令参数、聊天、日志或测试证据中。需要重新评测时保留旧结果，用新的输出目录记录新一轮证据，不能覆盖失败样本。

自定义验收/评测脚本退出码：0 通过、1 验收失败、2 环境阻塞、3 待人工评审；多种状态并存时按 2、1、3、0 决定进程码并保留逐项状态。外部测试工具仍保留自身退出码，由验收入口解释。

## 12. 九项任务与阶段出口

| 任务 | 交付重点 | 阶段约束 |
|---|---|---|
| 1 | 包结构、类型、配置、数据库、最小健康检查、锁文件 | 骨架 smoke 不等于 AC-01 全业务冷启动 |
| 2 | 三设备 MQTT 模拟器、三场景、命令回执 | 必须连接真实测试 Broker |
| 3 | 遥测入库、去重、顺序、当前状态 | 先完成后端规则，页面相关子项稍后验证 |
| 4 | 查询、历史与场景控制 API | 设备→消息→数据库→API 链路可复现 |
| 5 | 工单、证据、request_id 幂等与槽位 | 预置测试证据，不依赖尚未实现的模型循环 |
| 6 | 四工具、fixture/real provider、执行预算 | 真正调用业务服务，完成协议与故障分支 |
| 7 | 三页面、曲线、轨迹与错误展示 | 完成前后端集成与关键 E2E |
| 8 | 四服务部署、重启恢复、性能与稳定性 | 此时才完整判定 G1/G2 |
| 9 | 真实评测、人工复核、演示与求职材料 | 全部证据满足后才判定 G3 |

每个 AC 可能包含多个子断言。只完成部分时记录已覆盖子项，其余保持原状态；不得提前将整项置为 PASS。已有可靠证据可复用，但须说明与当前提交仍相容的依据。

## 13. 进度记录与会话续做

## 14. 证据、评分与完成标准

验收状态只使用 NOT_RUN、PASS、FAIL、BLOCKED、PENDING_REVIEW。任务 DONE 与验收 PASS 是不同概念；不得通过“任务已写完”推定验收已通过。

- AC-01—AC-40 的证据保存至 artifacts/acceptance/，关联当前 Git 提交、依赖锁、环境与执行时间。
- G1：物联网与网页基础；G2：加上 Agent 工程闭环；G3：全部交付与真实模型评测。具体编号以验收文档第 1 节为准。
- A01—A20 各执行 3 次，共 60 次案例执行；一例可包含多次 Agent run/模型调用，不能把案例数写成 API 请求数。
- 总成功数至少 54/60，各类别至少 9/12，关键错误为 0。案例独立初始化，A15/A16 在案例内部完成前置步骤。
- 程序核对工具与数据库，人工核对回答语义和关键错误。没有真实人工结论时保持 PENDING_REVIEW，不冒填 reviewer，也不把另一个模型裁判当成人工。
- 改动 prompt、模型、Schema、上下文组织或工单逻辑后，最终版本重新完成完整真实评测；纯样式修改按影响范围验证并说明沿用证据理由。
- API P95≤500 ms、遥测入库 P95≤1000 ms、60 分钟接收率≥99% 均为目标，必须按验收文档的环境、样本量和计算方法实测。
- 保留所有失败样本和环境阻塞；不能删困难案例、缩小分母、调低阈值或把异常请求从报告中隐藏。
- README、架构、设计取舍、已知限制、上游归属与 3—5 分钟演示完整后，才声明校招作品交付完成。

## 15. 不可接受的捷径

- 用固定回答、模拟工单号、硬编码评测答案或伪造工具轨迹满足测试。
- 把 fixture 运行称为真实模型效果，把计划指标写成实测成果。
- 把应用错误改成成功响应、删除失败测试、无依据放宽超时或验收标准。
- 将测试配置、固定时间、隐藏数据重置接口带入正常演示路径。
- 将 .env、API key、Authorization 头、用户认证文件提交仓库或交给应用模型。
- 修改用户其他项目、全局工具配置或真实工作数据来规避当前问题。
- 擅自改变这份约束文档来绕过当前失败；确需变更业务合同，记录原因并同步开发计划、验收规则及相关测试。

## 16. 向用户汇报的方式

用中文简洁汇报：本次完成什么、为何修改、实际执行了哪些验证、还剩什么、下一步是什么。引用真实文件路径和必要命令，不粘贴大量无关日志。

进行较长任务时，主动提供有信息量的进度更新。不要只输出计划后停止已授权的开发，也不要用“应该通过”“理论上可以”替代实际验证结果。必须提问时说明具体缺失项及其影响，避免重复请求已有授权。

最终交付前确认：代码改动可解释，相关验证有证据，未完成项如实标记，进度已更新，凭据未进入产物。简历只写实际实现且本人能解释的能力与数字。
