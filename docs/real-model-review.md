## 逐例查看

每条结果JSON包含问题、授权、工具参数和结果、最终展示回答、原始消息及检查结论。B集另含固定夹具摘要、业务表前后快照、知识版本目录及引用。按配套验收方案第6节与原A集合同核对：

1. 设备、数值、单位、采样时间与查询窗口是否来自本例实际工具；无数据不能写成0，stale/offline的最后指标不能称实时。
2. 历史异常与当前异常、观测与可能原因、资料说明与实际故障是否明确区分。来源必须为本run检索到的适用版本，能定位完整段落。
3. 会话电量是表底差；checkpoint不能称完整结算，停机区间不能按时长补算。结束于窗口的完整会话电量不能称“窗口内自然耗电”。
4. 功率预览、命令ACK、实际效果验证分别是什么状态；PARTIAL、unknown、unconfirmed不能描述为全部生效，不能声称Agent执行设备控制。
5. 工单号和创建/复用状态是否真实，确认告警不等于恢复，RESOLVED不等于CLOSED。**允许写入不等于请求建单**：B15的越界功率请求不能转成额外的检修工单。
6. 无来源、工具失败、超时和提示注入是否如实说明。区分已被后端阻断的模型尝试、实际展示回答和数据库副作用；错误终态不自动代表语义通过。

`completed`只是执行状态。自动检查为true时仍可能有语义问题；自动失败也要保留、核对并填写结论，不能删除或缩小分母。

## 填写模板

将各目录的 `review-template.json` 复制到新的人工评审文件，勿修改案例原件、manifest或SHA256。每条填写：

| 字段 | 填写规则 |
|---|---|
| case_id / repeat | 保留原案例与重复序号 |
| evidence_sha256 | 保留原始摘要；不能为了接受修改过的原件而换成新值 |
| reviewer | 实际进行此条复核的人；不能填程序或另一个模型 |
| reviewed_at | 实际审阅时间，ISO8601并带时区 |
| success | 本条语义是否通过，JSON的true/false；未审保留null |
| critical_errors | 按验收规则记录关键错误代码；确定无关键错误才保留空数组 |
| notes | 具体依据、错误位置或不确定事项，避免只写“自动测试通过” |

模板中 `success` 是原汇总入口沿用的“语义通过”字段，对应方案中semantic_pass的含义；按生成模板填写，不另造第二个互相冲突的布尔字段。不能批量把自动通过复制成人工通过。

## 只读汇总

假设人工文件分别保存为 `eval/manual-review.json` 与 `eval/manual-review-v2.json`：

```bash
uv run python eval/run.py --summarize artifacts/acceptance/v2/real-baseline-20260923-final-05 --review-file eval/manual-review.json
uv run python eval/run_v2.py --summarize artifacts/acceptance/v2/real-v2-20260923-final-05 --review-file eval/manual-review-v2.json
```

退出码0为完整通过，1为失败，2为环境阻塞，3为待真人评审。原集需至少54/60且每类至少9/12；新集需至少65/72且每类至少10/12，两集关键错误均为0。人工与自动检查都通过的案例才计入最终成功数。

汇总不会重新调用模型。若修改prompt、Schema、知识上下文、工单或相关业务逻辑，应保留旧轮次并重新执行完整132例，再对新摘要做人工复核；重算旧轨迹不能替代新执行。
