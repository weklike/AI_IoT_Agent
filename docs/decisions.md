# 实施决定

## 2026-09-22 / v2.0 方案定稿与关键取舍

- 两份 v2.0 文档按审阅意见修订后定稿为正式方案，范围未变；下列取舍在修订中确定并写入正文。
- **迁移是唯一建表路径**，停用 `Base.metadata.create_all`：FTS5 虚拟表无法由 ORM 模型声明，两条建表路径必然漂移；ORM 继续作为查询映射，另测模型元数据与迁移后 schema 是否一致。
- **冷启动自动导入知识索引**：backend 在迁移后按 `knowledge/` 内容摘要幂等导入，`scripts/index_knowledge.py` 降为显式检查与重建入口。否则空卷启动无法检索，与原 AC-01「不手动补数据库」冲突。
- **功率预览有效期 30→120 秒**：人工确认与演示讲解需要时间，而安全性由控制指纹而非有效期长度保证；指纹变化仍立即失效。
- **start 后维持 0 W**：让提升功率只有功率计划一条路径，站点预算不变量只需一处校验；代价是启动后需再执行一次计划，页面必须给出「等待功率计划下发」文字而不是显示成故障。
- **功率计划阶段内并行、阶段间串行**：逐台串行时先降后升最坏 54 秒必然突破 30 秒 deadline，并行后最坏约 18 秒才成立。
- **长周期阈值可在测试中覆盖**（投递过期 24 小时、巡检周期 30 分钟等）并登记白名单，否则相关 XAC 无法执行；控制、Agent、新鲜度等秒级时限一律不得放宽，只允许冻结 DataClock。
- **A19 已知限制不等于豁免**：仍计入原集 60 的分母并计为失败，失败边界类余量为 0，写入两份文档以免最终版本误判。

## 稳定性审查修正

- 固定 DataClock 会让多个工具 started_at 相同，因此增加 ToolCall.ordinal 保存执行顺序；不使用随机 UUID 的字典序代替时间顺序。
- 模型响应持久化也消耗业务总预算；保存后再次检查 deadline，不能在已过期时返回 completed。
- 模型失败/超时同样记录耗时；正常最终响应允许空 tool_calls 列表，但空正文仍为协议错误。
- 未授权或非法工具在执行前拒绝，同时保存服务器失败轨迹；不会进入业务服务。
- 场景超时更新若遇 SQLite busy，记录具名任务错误，不留下未检索异常。后续显式命令查询可持久化已经过期的状态，不通过隐藏循环重试写入。
- 场景 POST 尚未返回时离开详情页，取消请求并阻止后续响应重启旧轮询。
- 测试镜像以源码摘要命名并复用只读构建产物，每次容器/卷/端口/前缀仍独立；避免重复测试因不必要的镜像元数据网络请求被阻塞。
